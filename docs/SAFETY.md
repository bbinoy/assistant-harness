# Safety model

The agent can read your mail and act on your behalf, so most of the design is about limiting what it can do and making everything it does visible and reversible.

| Layer | What it does |
|---|---|
| Owner allowlist | Only your own *Note to Self*, from your own number, is ever acted on. Your linked device also receives all your other Signal traffic; it is dropped and logged with a masked number. (`guards.ts`, tested) |
| Tool policy | allow / ask / deny in `policy.ts`, tested against real tool names. Every tool the model might get declares an approval flag in one manifest (`toolmanifest.ts`): `no` (runs), `auto` (the approval judge below decides) or `yes` (always asks), for chat and for unattended runs separately, the same for every mail provider. Unknown tools default to `yes`, i.e. *ask*. What may run unattended depends on who is acting: the background mail handler, which reads untrusted mail with nobody watching, may only leave reply drafts, and never has a send judged. The never-allowed set (trading, delete, trash, spam, unsubscribe) and a group's rights are not flags: they stay hard rules in code. No tool input may reference a local file (`file://`), so an injected email cannot get `~/.ssh` or `.env` attached to a draft. |
| Approvals | The question is built from the exact arguments, never paraphrased by a model, and nothing is cut silently (invisible characters are shown as code points; for a draft only real quote lines are left out, any text below a quote marker is shown): a long email body is shown generously and any remainder is announced. Fail closed: a timeout or any doubt means *no*. Several approvals can be open at once: a reaction or a quoted reply answers its own question, a plain yes / no the newest chat one. A chat question waits `APPROVAL_TIMEOUT_MINUTES` (15), one from an unattended run `BACKGROUND_APPROVAL_TIMEOUT_MINUTES` (120); the question states the real wait. Edit-and-approve is limited to calendar create/update, never to recipients or attendees. A model judge for free-text replies returns constrained output; a rambling answer cannot become an approval. It is the same small model (and warm process) as the approval judge below, told which job it has in the first line of the prompt; an answer that names the other job is discarded, so a reply verdict can never pass as an action verdict or the reverse. An approval asked by an unattended run (a wake-up, the brief, the radar, the mail handler) is answered only by an explicit yes / no / 👍 / 👎 or by a reply that quotes the question; any other message you type meanwhile is a normal chat message, and the run does not hold the chat queue. **An edit is never an answer:** editing a message ("no" into "yes", or the reverse) cannot approve or decline anything, because the approval check is skipped for every edit and an edit of a message that was taken as an answer is dropped (`edit()` in `conversation.ts`, tested); an approval is answered only by a new message, a reaction on the question, or a quoted reply. |
| Approval styles | `APPROVAL_STYLE=strict` (default) is the row above, unchanged. `soft` and `conversational` are measured prototypes (docs/ARCHITECTURE.md, "Approval styles"). **Soft** lets the small model read each reply against all open approvals: it picks the approval, and a condition, partial answer, "later", hedge, question or sarcasm is not approval (the approval stays open, the owner gets a short clarifying reply); it fails closed (error, timeout, malformed or wrong-task answer, an id it was not given: no approval, the message goes on as chat, the owner is told the approval is still open); only a short message (200 characters) can consent; a bare "yes" with several approvals open asks which one; edits, voice and captions still never answer. It does NOT keep the guarantee that code alone decides what counts as yes: a wrong `approve` from the model on a short message is an approval, so soft is only as safe as the judge (measured: 0 false approvals in 70 replies; that is evidence on a small corpus, not a bound). **Conversational** also lets a model write the question. That removes the property "the owner sees code-rendered details": a model that read attacker text in the arguments (an email body, a web page) wrote what the owner reads. Mitigations, none of them a proof: a second independent call sees only the exact arguments and the question and must agree it is accurate and complete (recipients with roles, bcc, times, amounts, URLs), one retry, then the code text; every ask is audited with the full arguments, the question, the reply, the verdict and whether the call that ran has the same arguments (`npm run report`, "Approvals: question vs arguments"). The check catches questions that misstate the arguments; it cannot catch arguments that are themselves wrong or hostile but described truthfully (a bcc to an attacker that the question states plainly is still a decision the owner must read). Measured results: docs/ARCHITECTURE.md. |
| Clean at the door | Untrusted text is cleaned where it first enters, by one shared sanitiser (`sanitize.ts`), so hidden or look-alike content never reaches a model: zero-width, bidi, tag-block (invisible ASCII), stray variation selector, control and private-use characters are dropped (emoji joiners, VS16, flags and Persian ZWNJ survive), text is NFC-normalised, lengths are capped with a visible `[... N characters cut]`, absurd runs collapse. HTML (mail, web) is parsed with parse5 and only the visible text is kept (`html.ts`: comments, script/style/head/template, `hidden`, display:none, font-size:0, opacity:0, off-screen, zero-size and same-colour text are dropped; best-effort, no browser engine). Applied to Signal messages, captions, quotes, names and voice transcripts (`conversation.ts`), mail rows and bodies (`heartbeat.ts`, `mailtext.ts`), digests, every `fence()`, and every tool result the model reads (the SDK PostToolUse hook rewrites the output, `toolclean.ts`). Fences cannot be closed or forged, nor batch headers and speaker marks. The log shows counts only (`clean: ... removed N hidden character(s)`). |
| Reversible by default | Mail is only archived (never deleted), every archive is recorded with ids, and `npm run restore <id>` brings it back. At most 25 archives per tick. There is no keyword blocklist: the classifier decides by intent (what is left to do), and the morning brief lists every archived mail with its reason so you can scan for a mistake. |
| Memory | Only a chat you started can change it, and every change is mentioned in the assistant's own reply and logged (if it replies with only a reaction, a short notice is sent instead), so a mistake is seen and undone with a message. The brief, the mail handler and the heartbeat cannot touch the notes, and the file tools chat gets are confined to `memory/notes/` by policy (a group's, to its own notes folder). Notes are injected into background runs as fenced data and can shape tone, priorities and sorting but never permissions: policy and suspicious-text isolation are code. A note the assistant saved because a hostile email told it to is the residual risk: it is caught by the announcement, not prevented. Changes are audited by outcome, never by content. |
| Reply drafts | A reply the background handler drafted is shown to you on Signal and is never sent unprompted. Sending it is a chat send: the judge decides from your message and the exact draft, and when it does not clearly say go ahead you are asked, with the draft read back from Mailbird at that moment (recipients, Cc, Bcc, subject, new text, attachments), not the model's description. If the draft cannot be read back, nothing is sent. |
| Gmail | With `MAIL_PROVIDER=gmail` the connector comes through your Claude login; the same layers apply (manifest, approvals with the real recipients, the sanitiser on every result). Added in code (`gmailrules.ts`, `policy.ts`): trash, spam, delete, untrash, unsubscribe-style tools, attachment content, label deletion and the raw MIME format are denied; any label tool that names `TRASH` or `SPAM` (add or remove) is denied whatever the tool; an archive is only "remove INBOX from a thread" and is log-only (`would-archive`) until `GMAIL_ARCHIVE_LIVE=true`; attachment content is stripped from results before the model reads them. A send, reply or forward always shows its real recipients: a reply that names none is shown with the people of the original message read back from Gmail, a send of a draft with the draft read back, and a call that cannot be read back is not sent. The only mail the assistant may send without asking is the brief to `MAIL_SELF_ADDRESS` (`BRIEF_EMAIL=on`, brief run only): the address must be the only recipient, with no cc, bcc, attachment, draft or thread. The heartbeat reads Gmail through a small relay run that may make only the planned calls with exactly the planned arguments; its tool results are captured by code, not taken from the model. |
| Chat only | With `MAIL_PROVIDER=none` there is no mail client in the agent at all: nothing connects to Mailbird, the Mailbird server is added to the hidden connectors so none of its tools is sent to the model, and the mail skills are not offered. This only removes capability; `policy.ts` and every approval rule are unchanged, so a mail tool that somehow appeared would still be classified exactly as before. |
| Approval judge | A small model gives a second opinion on a few approvals (`src/autojudge.ts`). It can only loosen, and only inside a floor set in code: calendar events with no attendees; a NEW event from any source, changing an existing event only in chat (an existing event may have guests who would be emailed); opening a web page, in chat and in your own background jobs (wake-ups, the brief, the radar) and only for a plain https address on a named public host (no IP address, local name, port, login, fragment or long query, since an address can carry data out); the judge decides from your own message, or from the instructions the job was given, whether the page is what is needed, and never sees mail or page text. The mail handler (raw untrusted mail, nobody watching) always asks. Sharing and anything else involving other people always asks, whatever it says. **Sends and forwards of mail**: in chat the judge decides from your own recent messages and the exact draft (read back from the mail client, with every recipient including Bcc, the subject, the text and whether there are attachments): it says go ahead only when you asked for exactly this send, to these recipients, and nothing is unexpected; if the send was the assistant's own idea, you only asked for a draft or a reply, or anything is unusual (an extra recipient or Bcc, other text, an attachment, a recipient you never mentioned), it asks you. Unattended runs (the brief, the radar, wake-ups and above all the mail handler, which reads raw untrusted mail) and groups never auto-send: a send there always asks. Drafts need no approval, because nothing leaves your mailbox. Residual risk: the draft text is written by the model, possibly after reading a hostile mail, and the judge reads it; it is fenced as data and the judge may only choose between auto and ask, but a hostile draft that talks the small model into auto is the cost of skipping the question. `AUTO_APPROVE=shadow` or `off` makes every send ask again. It sees the exact arguments rendered by code and, in chat, your own message, never an email; its answer is constrained JSON and anything unclear, slow or broken means "ask". Default mode is `broad`; every skipped question is logged (audit `auto-approved`, with the judge's reason) but not announced, to keep it frictionless; `npm run report` lists them. An approved (or auto-approved) call is not asked about or repeated again within 30 minutes: the same tool with the same arguments is refused as already done. `AUTO_APPROVE=shadow` makes it judge and log while you still decide (`npm run report` compares its verdicts with your answers); `off` disables it. |
| Web | In chat only. Searching is allowed (a question you typed; results are snippets and links). Opening a page asks on your phone first, showing the exact address, because an address can carry data out. Your chat's unattended background run (a gate task, policy source `background`) may also search, and a page fetch asks there too. The mail handler gets neither, since it reads untrusted mail with nobody watching; the brief and the radar may open a page (the judge decides, as above) but not search. Web content is treated as untrusted, like mail; the agent is told never to put private data in a search or an address. Residual risk: a search query itself is a small channel to the search provider (and a background run reads mail snippets); accepted for the background run because every write and every page fetch still asks on your phone. |
| Skills | Only the skills that ship in `plugin/skills/` can be loaded: the SDK's skills allowlist refuses any other (checked: asking for another skill returns "not in this session's skills allowlist"). They hold no personal data; your calendars, Notion pages and writing style are in your memory notes. |
| Proactive radar | A background run (chosen by your chat's gate) that can only read, plus write a meeting prep page in Notion. It returns messages as constrained JSON; code decides whether they may be sent (never twice: the keys of what it sent are read back from the conversation log; at most 3 per run and `MAX_PROACTIVE_PER_DAY` of its own messages per day counted from its ledger lines in the log (mail alerts do not use it up); never within 30 minutes of its last run, before today's brief, at night, while paused or over the spend limit). It is owner-only: a group's gate output can never start it. A calendar change or a sent mail still asks on your phone. `PROACTIVE=off` turns it off. |
| Written vs fixed messages | Two informational messages are written by a model from facts (`src/notice.ts`): the heartbeat's new-mail alert and the handler's report. The facts (sender, subject, reasons: all mail text) are fenced as data to a tool-less Haiku; code accepts the text only as plain text of at most 600 characters with no link, no number that is not in the facts and every draft id copied exactly, and otherwise sends the fixed template, so a prompt-injection subject can at worst shape the wording of a short note, never trigger anything. These stay code on purpose: approval questions (the exact arguments shown), the draft shown for sending, the memory-change announcement (the owner sees exactly what was saved), error, login and usage-limit notices (they must work when the model does not), the voice failure note and "Applied your change". |
| Spend guard | A daily ceiling pauses *background* work (brief retries, the handler); chat stays available. |
| Robust state | State files are written atomically and updated synchronously: no torn files after a crash, no lost updates between concurrent parts. Settings are validated at startup, so a typo stops the agent instead of misconfiguring it. |
| Observability | `logs/audit.jsonl` records every tool decision (ids, never email content, for chat). `logs/agent.log` is redacted (numbers, tokens; every console level, not only log and error) and rotated; the audit log has credentials masked too. Child processes that read files or network data other people control (ffmpeg, whisper, Kokoro, signal-cli) start without any key, token or secret variable. `npm run report` shows what the heartbeat did, `npm run triage-check` shows what it *would* do with your newest mail without acting, and `npm run doctor` warns if the heartbeat has stopped ticking. |
| Kill switches | `touch state/paused` pauses everything (put a date inside to resume on it). `HEARTBEAT_ACTIONS=log` makes the heartbeat record decisions without acting. |
| Edits and deletes | Signal lets people edit a message and delete it for everyone. Both are untrusted input like any message (sanitised, fenced as data in the prompt), and both are accepted only from the original's author: the sender is compared with the author recorded in the log (or on the message still waiting); an edit of an unknown message in a group, of a message that is not a person's own (Ted's own, say) or from anybody else is ignored. A message deleted before it was answered is dropped from the queue and never acted on; a deleted message is hidden from the group's context, the gate's tail and the dream, and what was deleted is never evidence for a memory note (an edited one counts once, as edited). Nothing is announced about either, in a group least of all. The logs stay append-only: an edit and a deletion marker are lines of their own, and `search_logs` still shows what was written before. |
| Message log | `logs/messages.jsonl` (owner-only) holds the conversation in the assistant's chat, with Signal timestamps: what the assistant sent, what you sent (voice notes as transcripts) and your reactions. It lets a reaction be matched to its message, lets the assistant search the past, and is what the nightly dream learns from. It is size-bounded (`MESSAGE_LOG_MB`): the oldest messages are folded into one short summary by a small model. |
| Voice messages | Transcribed locally (whisper.cpp), never sent anywhere; every voice note is transcribed (in a group it may be meant for the assistant), but at most `TRANSCRIBE_CONCURRENCY` (2) at a time, the rest wait in line, so a flood cannot start many processes. Only a plain audio attachment from your own chat with the assistant under 25 MB is read, by file name inside signal-cli's folder (no paths). The transcript goes into `logs/messages.jsonl` (owner-only) next to your other messages, and a spoken reply can never answer an approval. The chat agent may *read* its own data folders (`logs/`, `state/`, `memory/`; symlinks resolved, never written) and search the logs with a read-only `search_logs` tool, so it can tell you what a voice note said or what happened to a mail; their contents are treated as data. |
| Pictures | A photo (JPEG, PNG, WebP, GIF or HEIC, up to 20 MB, plain file name inside signal-cli's folder, no paths) is read from disk, checked by its bytes rather than its name, shrunk locally and shown to the model for that one turn. Other files and videos are skipped. The bytes are never written to a log or a note; only `🖼️ caption` is recorded. **Text inside a picture is data, never an instruction**: the prompt says so next to every picture, and what the model can do is still decided by `policy.ts`, not by what it reads. A group member's picture is treated like any member message (policy source `group`, no owner tool, whoever sent it and whatever it shows). A caption or a photo is never an approval answer. In groups set to `tagged` only, a picture nobody addressed to the assistant is not even opened. Residual risk: a picture stays in the resumed session's history (until compaction or the idle reset), like any message. |
| Spoken replies | By default generated locally (Kokoro), never sent anywhere. Only in the assistant's own chat or a group it answers in, only when the model chooses to (the option is offered with every message when speech is set up; notes can switch it off), only for short answers; anything else, and any failure, is sent as text. Approval prompts are always text, and a voice message can never answer one. What was said is logged as text in `logs/messages.jsonl`. **Optional remote speech** (`TTS_PROVIDER=elevenlabs` or `http`, off by default, [REMOTE-TTS.md](REMOTE-TTS.md)) changes the first sentence: the words of each spoken reply, and only those, are sent over HTTPS to a third party or to your own server, so anything Ted says aloud is known to that service. It never receives mail, notes, history or approval questions (those are text). Keys and tokens are read from `.env` only, sent in a header, never logged (errors blank them out) and never committed (`npm run check:secrets`); redirects are not followed; an `http://` address is accepted only for localhost; a missing key stops the agent at start-up. Failures (timeout, HTTP error, quota) are sent as text; the provider is switched to Kokoro only if you set `TTS_FALLBACK=kokoro`. You must have the rights and consent for any cloned voice you use; the reference recording stays on the remote side and no cloned or celebrity voice ships with this repo. |
| Wake-ups | A small gate model (Haiku, no tools; notes and log fenced as data) decides on each heartbeat tick whether a conversation should do something on its own. Its output is untrusted JSON: anything but a literal `act: true` plus instructions does nothing. Code, not the model, guards the rest: pause, the daily budget (`budgetSpent()`, which never consumes the owner's notice), the owner's quiet hours, the next look clamped to 15 to 60 minutes (and the group debounce). There is deliberately no per-conversation cap on wake-ups and no cap on a group's replies per hour: the remaining guards are pause, the daily spend limit, quiet hours, the 15-minute floor between looks and the gate's own judgement. A group's wake-up runs the group run (policy source `group`), never an owner tool. Your chat's wake-up runs with policy source `background`: reads allowed, web search allowed (page fetches ask), no note files, every write asks on your phone. The gate may also choose the presets `brief` and `radar` for your chat only: the gate output is `task: "task" | "brief" | "radar"`, anything unknown is the plain task, and a group asking for a preset gets the plain group task or nothing (`buildTask`, tested). The model chooses only WHEN; the profile (policy source, tools, limits, schema) is fixed in code (`PROFILES` in `src/agent.ts`). The brief has a deterministic backstop that stays an override of the notes (a note saying "no brief" or "brief at 11" does not stop it): no brief logged today by `BRIEF_BACKSTOP_HOUR` (9), or an incomplete attempt, and code runs it (dream first, at most `BRIEF_MAX_ATTEMPTS` a day, the owner told when it gives up). The instructions come from a model that read your notes and log (which can include mail snippets in earlier notices), so they are shown to the run as data and cannot widen the policy. Failures are logged and silent. Groups are woken only when the assistant runs on its own Signal account (never on Note to Self, where it would post as you). |
| Group chats | Only in groups you are a member of (checked against the group's member list; if it cannot be checked, no answers, nothing logged and no voice message is even transcribed), a small gate model (no tools, group text fenced as data) decides when to speak, only with the assistant's own Signal account. The run has no private data: the tool policy denies everything but web search, the file tools on a path strictly inside that one group's notes folder (`..` and symlinks resolved first, `src/contain.ts`; the one gate on what it may write) and the memory tools of a server bound to that one group (forget a note, search its log, undo its dream), in code, whatever anyone writes, including you. Its Claude Code session loads no user settings, no connectors and no skills. The one warm process kept for the latest group (`WARM`) is built from that same isolated set of options for that one group and handed to nobody else (a different group, a changed session or notes index: it is closed instead); the owner's warm process is never handed to a group; the gate's warm Haiku process carries no conversation (only the gate's rules and a one-line style summary in its options, no tools, no connectors, no memory: the conversation's text arrives only in the prompt) and only the exact system prompt it was built with may use it. Warm processes together are at most three, about 200 MB resident each, no tokens; one that died is replaced by a cold start; the gate's answer delay is capped in code (`GATE_MAX_DELAY_SECONDS`). `npm run check:isolation` proves it against the real SDK: a canary in your notes and logs never appears and reads of your notes are denied. The only thing shared from your private memory is your personality (`style` notes). Other people's text is fenced data, never instructions. Each group has its own notes (memory/groups) and history (logs/group-*.jsonl), separate from yours; the group's dream reads only that group's words, writes only that group's notes (snapshotted, undoable), and your own dream never sees any of it. A member can plant a note, but only in that group's own memory, and a note is bounded where it is read (how many a prompt includes), not when written, as with yours. A group's memory changes are not announced on your phone: its reply says what it saved. |
| Nightly dream | The run that updates memory has **no tools**: it answers with JSON and code decides what is applied. A new note needs a verbatim quote of *your own* typed or spoken words (checked in code, so a mail, a handled-mail message or a reaction's target cannot plant a memory); a merge may only shorten what it merges; expired notes are checked against their date; `setup-` and `voice-` notes are off limits; at most 8 writes and 12 deletions per run (a bound on one night's changes, not on how many notes you can have). The notes are snapshotted first (7 kept), the changes are logged (not announced), and "undo the dream" restores them. |

Known limits: `signal-cli` stores its keys unencrypted on disk (keep FileVault on); its local socket is unauthenticated (it listens on `127.0.0.1` only); anything running as your user can reach it. Prompt injection cannot be solved, only contained: the design above limits what a hostile email can make the agent do, it does not make it impossible to try.
